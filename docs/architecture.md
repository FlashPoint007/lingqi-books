# 架构与实施边界

## 一、Sites 层

React 页面 + Worker API。浏览器只请求统一 `/api/catalog`；服务端负责来源参数、超时、缓存、结构归一化和错误隔离。封面、漫画图像直接来自来源 CDN，没有开放 URL 代理。

目录对象：`source:id / title / originalTitle / kind / language / author / cover / tags / score / votes / url / readable`。`readable` 表示支持阅读流程，不是中文章节一定存在的保证，实际目录返回为空时必须显示原因。

Bangumi 评分不与 MangaDex 的收藏量混淆。匹配第一阶段保留用户确认，后续应落库 `work_source_links`，记录内容类型、卷号、作者、语言、匹配分数、人工确认和更新时间。搜索失败应与“没有结果”区分。

## 二、扩展执行层（尚未部署）

Sites 是 Worker 环境，不适合直接运行 JVM、Android APK 扩展或带原生依赖的阅读器运行时。建议把漫画扩展与小说解析放在自有容器服务，Sites 仅调用经过认证的 HTTPS 接口。

漫画侧优先验证 Suwayomi 作为扩展执行引擎，再决定是否需要 Maki 的采集和书库能力。两者并不是同一层的可互换插件。验证顺序：健康检查 → 指定允许的扩展列表 → 关键词搜索 → 目录 → 一章图片 → 超时 / 限流 / 移除请求。固定版本，记录扩展标识与版本，不自动安装全部第三方扩展。

小说侧需要独立 LNReader 插件宿主，补齐插件所需 fetch、HTML 解析、持久化与运行时 API。先选择具有授权证据的单个源，完成搜索 → 作品 → 目录 → 正文 → 编码与分页测试；不要在 Worker 中 eval 远程插件，也不要把用户 Cookie 发布到浏览器。

建议的桥接契约（设计草案，当前没有对应在线端点）：

- `GET /v1/sources`：返回实际允许且可用的来源及能力。
- `GET /v1/search?source=<id>&q=<text>&page=1`：返回作品候选和准确的分页信息。
- `GET /v1/works/<id>`：返回语言、类型和署名信息。
- `GET /v1/works/<id>/chapters`：返回目录和可用状态。
- `GET /v1/chapters/<id>`：仅返回纯文本段落或受控图片 URL，包含来源 URL 和署名。

桥接服务需验证服务端密钥、目标域白名单、源并发限制、请求日志脱敏及错误分类。管理接口只向运营者开放；不暴露任意目标请求、文件路径读取或插件安装给访客。

## 三、中文内容接入验收

每个来源应保存：授权或允许使用依据、语言、版权范围、署名方式、更新方式、可用地区、样本作品、搜索耗时、目录耗时、正文成功率、下架渠道、最后验证时间。不把“GitHub 存在插件”当成内容已授权或源仍可用的证明。

小説家になろう只支持经条件核对后的日文发现，不作为中文正文池。当前适配器由 `NAROU_ENABLED` 控制，默认禁用。

## 四、后续优先顺序

1. 确认一个可用且允许接入的中文日轻正文源，跑通实际阅读链路。
2. 独立扩展服务与首个授权漫画 / 小说插件端到端验证。
3. D1 + 身份鉴权，实现跨设备书架、进度和持久化匹配；先定义用户数据隔离，再公开账户功能。
4. URL 路由与分享、书架备份导入、内容源可观测性、共享缓存和全局限流。
5. 按季度 / 类型的推荐，以及评分人数门槛，避免低样本高分条目占榜。
